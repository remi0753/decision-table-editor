# 9. デバッグ・トレース

## 9.1 ステップ実行トレース

評価パネルで入力値を指定して評価を実行した際、評価の経路を可視化する。

### 評価パネルの入力フォーム

評価実行前に、ロジックのフィールド定義に基づいて動的に生成されたフォームで入力値を指定する。フィールド型に応じた専用UIを提供し、JSONの直接入力は行わない。

| フィールド型 | 入力UI                                             |
| ------------ | -------------------------------------------------- |
| `string`     | テキスト入力                                       |
| `number`     | 数値入力（数字のみ受け付ける）                     |
| `bool`       | 「はい / いいえ / （未入力）」の3択ラジオボタン    |
| `enum`       | 選択肢ドロップダウン（先頭に「（未選択）」を追加） |
| `date`       | 日付ピッカー                                       |
| `datetime`   | 日時ピッカー                                       |

- すべてのフィールドは省略可能。省略した場合は `null` として評価する
- 省略されたフィールドは「（未入力）」と表示する
- 「評価を実行」ボタンを押すと下部にトレース結果と最終出力が表示される

### 評価結果の表示

終端結論に到達した場合、到達したテーブルの出力列名（`outputCol.name`）と値のペアをユーザーに表示する。技術的なIDは一切見せない。継続参照セマンティクス上、複数のテーブルの出力が同時に返されることはない（first-match により必ず1つの終端テーブルにのみ到達する）。

```
評価結果:
  対応手順: 解約金（¥XX,XXX）の案内をする。分割払い移行手続きを説明する。
  転送先電話番号: 03-1234-5678
```

### トレース表示

```
トレース表示の例:

  [ステップ1] テーブル「初期審査」を評価
    行1: 顧客種別 = 法人 ✓、申請金額 >= 1000000 ✗ → スキップ
    行2: 顧客種別 = 法人 ✓、（ワイルドカード）→ マッチ
    結論: → テーブル「詳細審査」へ継続

  [ステップ2] テーブル「詳細審査」を評価
    行1: 地域 = 東京 ✗ → スキップ
    行2: 取引年数 >= 3 ✓ → マッチ
    結論: "承認"（終端）

  最終結果: 承認
```

- 各ステップで、各行がマッチしたか・しなかったかとその理由を表示する
- マッチした行は緑でハイライト、スキップされた行はグレーで表示する
- テーブルのDAGグラフ上でも、実際に辿られた経路をハイライトする

### NO_MATCH（結果なし）時のトレース表示

評価の終了条件が `status: "no_match"` の場合、発生した場所によって2パターンのメッセージを表示する。

パターンの判定: TraceStep の `depth` フィールドで区別する（`depth == 0` → パターンA、`depth >= 1` → パターンB）。

**パターンA: エントリーテーブルでNO_MATCH（最初のテーブルからマッチしなかった）**

```
評価結果: 結果なし（エラー色）

入力値に当てはまるルールが見つかりませんでした。
テーブル「初期審査」のルール行を確認してください。
→ どの条件にも当てはまる場合のルール行を末尾に追加することを推奨します。
```

**パターンB: 継続参照先テーブルでNO_MATCH（途中のテーブルでマッチしなかった）**

```
評価結果: 結果なし（エラー色）

テーブル「詳細審査」でマッチするルールが見つかりませんでした。
特定の入力値でこの経路に入った場合に結果が得られないことがあります。
→ テーブル「詳細審査」の末尾にデフォルト行を追加することを推奨します。
```

- 「結果なし」はエラー色（赤またはオレンジ）で強調表示する
- 最終出力エリアは表示せず、代わりに上記メッセージを表示する
- ユーザーに技術用語（`no_match`、`status`、`entryTable`）は見せない
- どちらのパターンも、直前までのトレース詳細は通常と同様に表示する

## 9.2 インポート時の実行トレースリセット

ロジックデータのインポートが成功した際、**評価パネルの実行トレースは必ずリセットする**。

**理由**: インポート前のトレース結果は旧ロジックに基づいたものであり、インポート後のロジックとは対応しない。古い結果が残ったままでは、ユーザーが誤った内容を参照してしまう恐れがある。

**仕様**:

- JSONファイルのインポートが正常に完了した時点で、実行トレース（`evalResult`）を `null` にリセットする
- 自動修復を伴うインポートの場合も同様にリセットする
- インポートに失敗した場合（バリデーションエラー、JSONパースエラー）はリセットしない
- 評価フォームの入力値（`evalInputs`）はインポート時にはリセットしない（入力値は新ロジックで再利用できるケースがあるため）

**状態管理**:

`evalResult` は `uiStore` で管理し、インポートフック（`useImportLogic`）がインポート完了後に `clearEvalResult()` を呼び出すことでリセットを実現する。

## 9.3 「このテーブルを参照している親」の表示

テーブルを編集中に、そのテーブルを継続参照している親テーブルの一覧を右ペインのサイドバーまたはヘッダー近傍に表示する。

- 「このテーブルはテーブルA・テーブルBから参照されています」
- 親テーブル名をクリックすると、そのテーブルに移動できる

これにより、編集の影響範囲を事前に把握できる。
